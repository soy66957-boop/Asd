# Шесть документов: спецификация до кода

## Суть

Спецификация — это шесть файлов, а не один. Каждый отвечает на свой вопрос,
и план стройки пишется только после того, как владелец одобрил все шесть.

| № | Файл | Отвечает на вопрос | Ворота (без них документ не сдан) |
|---|---|---|---|
| 1 | `1-ПРОДУКТ.md` | зачем, для кого, что входит и что нет | «Готово, когда»: пронумерованные пункты «да/нет», каждый проверяется запуском |
| 2 | `2-ТЕХНИКА.md` | из чего собрано, как части говорят друг с другом | каждый внешний факт со ссылкой; каждый выбор со ссылкой на решение владельца или вариант |
| 3 | `3-ПУТЬ.md` | какие экраны, куда ведут | у каждого экрана состояния: загрузка, пусто, ошибка, без сети |
| 4 | `4-ДИЗАЙН.md` | как выглядит и движется | контраст **посчитан формулой** по парам токенов, а не прикинут на глаз |
| 5 | `5-ДАННЫЕ.md` | что где лежит | настоящий SQL/типы, не описание; где личные данные и по какому закону |
| 6 | `6-ЭТАПЫ.md` | в каком порядке строить и почему | что делает владелец; причина порядка; риски стройки |

Шаблоны: `шаблоны/1-ПРОДУКТ.md` … `шаблоны/6-ЭТАПЫ.md` в папке этого скилла.

## Когда не брать

- Правка в одну строку или баг с известной причиной: спека не нужна.
- Допрос не пройден: сначала `grilling`, иначе в документы попадут догадки.
- Нужна задача в GitHub, а не продукт: `gs-spec`.

## Порядок

1. **Прочитать манифест** дела: решения владельца (М1…), варианты (Т1…), исследование.
2. **Прочитать код, к которому примыкает новое.** Файлы, строки, форматы данных.
   Каждый факт о существующем коде в документах идёт со ссылкой `файл:строка`.
3. **Проверить внешние факты у первоисточника** (документация API, лицензии,
   шрифты, лимиты): `context7`, WebFetch официальной страницы. Не удалось
   проверить → в тексте «проверить при стройке», а не утверждение.
4. Писать по порядку 1 → 6. Продукт задаёт, что строим; остальные не
   добавляют возможностей, которых нет в продукте.
5. **Посчитать то, что считается:** контраст (формула WCAG по всем парам
   токенов), вес данных, число сообщений в сутки, бюджеты. Скрипт, а не глаз.
6. Прогнать тексты по стеку: antislop, humanizer, stop-slop; никаких длинных
   тире и «не X, а Y» (`СТЕК-ДИЗАЙН-И-АНТИСЛОП.md`).
7. Записать в манифест: фаза «черновик готов», ключевые находки.
8. **Показать владельцу** коротко: что в каждом документе и что нашлось.
   План стройки только после его «да».

## Что попутно собирать

- **Идеи для смежных систем** (`ИДЕИ-ДЛЯ-<система>.md`): что улучшить в том,
  с чем новое соединяется. Пометка «нужно новому» или «по желанию».
- **Уроки прошлых работ** владельца и свои (`Правила-из-ошибок.md`,
  `УРОКИ-ИЗ-РОЛИКОВ.md`): каждый урок, который применим, становится требованием
  с проверкой.

## Частые ошибки (каждая уже случалась)

| Ошибка | Что сделать вместо |
|---|---|
| контраст «примерно 4,9:1» на глаз | скрипт по формуле; в реальном случае глаз пропустил пару 4,32 |
| «работает как в рабочем приложении» без ссылки | `файл:строка`, прочитано сегодня |
| экран без состояний | таблица состояний у каждого экрана |
| «метрика: конверсия» | как считаем, откуда события, какой порог |
| «Готово, когда: всё работает» | 10–20 пунктов, каждый проверяется запуском |
| факт о чужом API по памяти | первоисточник или пометка «проверить» |
| скилл спеки заточен под другой мир (GitHub-задачи) | взять его стандарты, а выдачу — этими шестью файлами |

## Красные флаги — остановиться

- пишу план стройки, а владелец ещё не одобрил шесть документов;
- в документе число, которое я не посчитал и не нашёл в источнике;
- в продукте есть возможность, которой нет ни в пути, ни в данных (или наоборот).

## Проверка скилла

Базовый провал (без скилла) взят из реальной работы 19.09.2026 (магазин
Veritas Odor): контраст на глаз, скилл спеки не под задачу, пропуски в
пробах. Прогон с агентами под давлением не делался: агентов владелец не
запускает. Первый прогон со скиллом — следующая спецификация; найденные там
отговорки дописываются в «Частые ошибки».

```js
// Контраст пар цветов по формуле WCAG 2.x.
// ⚠️ Зачем скрипт: 19.09.2026 контраст «прикинутый на глаз» пропустил пару
//    4,32:1 (золото на карточке), а мелкому тексту нужно 4,5:1.
//
// Запуск: node контраст.cjs "#B5864F:#4A080C" "#F5E2C8:#581016" ...
//         node контраст.cjs --файл пары.json   ([["#fff","#000","подпись"], ...])
const fs = require("node:fs");

function яркость(hex) {
  const h = hex.replace("#", "");
  if (!/^[0-9a-f]{6}$/i.test(h)) throw new Error(`не цвет: ${hex}`);
  const [r, g, b] = [0, 2, 4].map((i) => parseInt(h.slice(i, i + 2), 16) / 255)
    .map((v) => (v <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4));
  return 0.2126 * r + 0.7152 * g + 0.0722 * b;
}

function контраст(а, б) {
  const x = яркость(а), y = яркость(б);
  return (Math.max(x, y) + 0.05) / (Math.min(x, y) + 0.05);
}

function вывод(к) {
  if (к >= 7) return "AAA";
  if (к >= 4.5) return "AA: любой текст";
  if (к >= 3) return "только крупный текст (от 24px или 19px жирным) и элементы";
  return "НЕ ГОДИТСЯ";
}

let пары = [];
const и = process.argv.indexOf("--файл");
if (и > -1) пары = JSON.parse(fs.readFileSync(process.argv[и + 1], "utf8"));
else пары = process.argv.slice(2).map((п) => п.split(":"));

if (!пары.length) {
  console.error('нужны пары: node контраст.cjs "#текст:#фон" ...');
  process.exit(2);
}
let провал = 0;
for (const [текст, фон, подпись = ""] of пары) {
  const к = контраст(текст, фон);
  if (к < 4.5) провал++;
  console.log(`${текст} на ${фон}  ${к.toFixed(2)}  ${вывод(к)}  ${подпись}`);
}
console.log(`пар ниже 4,5: ${провал}`);
```

# Суперплан — как браться за задачу

Собрано поиском по своей же базе (правило второе из [[00-Два-главных-правила]])
и проверено на деле: 19.09.2026 по этой цепочке пройден магазин Veritas Odor в
Telegram, от исследования до плана с ревью. Каждая фаза закрывается своим
инструментом и оставляет файл, который переживёт сессию.

⚠️ **Не вся цепочка на каждую задачу.** Двенадцать фаз ради правки одной строки
сожгут больше, чем сберегут. Глубина выбирается по цене ошибки (в конце файла).

```
Ф0 манифест ─> Ф1 исследование ─> Ф2 допрос ─> Ф3 материалы владельца ─> Ф4 варианты
   ─> Ф5 шесть документов ─> Ф6 план ─> Ф7 ревью плана ─> Ф8 цель ─> Ф9 исполнение
   ─> Ф10 приёмка и сдача          Ф11 «застрял» — в любой момент
Сквозное всё время: запись ошибок · идеи смежным системам · стек под работу · «один раз»
```

## Ф0 — манифест: заводится первым

Файл `МАНИФЕСТ-<дело>.md` рядом с работой, **до первого вопроса владельцу**.
Разделы и правила ведения — в конце этого файла. Хук SessionStart находит
незакрытые манифесты сам, поэтому имя начинается с `МАНИФЕСТ-`.

**Выход фазы:** манифест с целью словами владельца и таблицей фаз.

## Ф1 — исследование: когда ответ лежит во внешнем мире

Нужна, если решение зависит от того, чего нет в коде: рынок, закон, чужие API,
опыт других, цены. Не нужна для внутреннего бага.

| Шаг | Инструмент | Что даёт |
|---|---|---|
| метод | [[claude-skills--deep-research]] | переформулировка, 2–4 проверяемые гипотезы, план, источники, проход «против себя», `refresh_targets.md` |
| рынок, сегменты | [[claude-skills--market-research]] | размер рынка двумя способами, сегменты по Котлеру |
| конкуренты | [[claude-skills--competitive-teardown]] | 12 измерений, SWOT, карта позиций |
| сравнить варианты по источникам | [[feynman--source-comparison]] | таблица источников по вопросу |
| поиск | WebSearch, `perplexity`, плагин `exa` | свежие источники |
| документация | `context7`, WebFetch официальной страницы | первоисточник вместо памяти |

**Правила:** тезис держится на ≥3 независимых источниках разного типа, иначе
помечен «мало данных»; пристрастные источники (агентства, продавцы) помечены;
цитаты дословно в `sources/`; противоречия источников выписаны, а не сглажены.

**Выход:** папка `исследование/`: `plan.md`, `sources.csv`, `sources/цитаты.md`,
`<дата>_decision.md` (главное в 5 строках, гипотезы, риски, вопросы владельцу),
`refresh_targets.md`.

## Ф2 — допрос: понять, чего хотят на самом деле

**Основной инструмент — [[grilling]]** (`/grill-me`): дерево решений кругами,
все вопросы фронта разом, к каждому рекомендуемый ответ.

> **Искать факты — моя работа.** Если вопрос упирается в факт, его проверяют
> запуском до вопроса или между кругами (так 19.09.2026 API отзывов Авито
> проверен запросом: отдаёт 1 отзыв из 3, и вопрос владельцу стал точнее).

> **Работа не начинается, пока владелец не подтвердит, что поняли одинаково.**

Вопросы берутся из раздела «чего исследование не решило». Каждый ответ сразу
в манифест: решение, **следствие** для работы (что отсюда вытекает).

| Запасной | Чем отличается |
|---|---|
| [[ao-interview-me]] | по одному вопросу, мягче |
| [[sp-brainstorming]] | сократический разбор сырой идеи |
| [[ao-idea-refine]] | заострить идею, проверить допущения |
| [[grill-with-docs]] | термины в `CONTEXT.md`, решения в записи о решениях |

**Выход:** решения М1… в манифесте, каждое с причиной и следствием.

| Что прислано | Чем брать |
|---|---|
| видео | [[bradautomates--watch]] (кадры, речь); быстрый текст на экране — листы кадров `ffmpeg -vf "fps=1/2,scale=320:-1,tile=4x2"`, последний кадр `-sseof -1` |
| фото, скриншоты | Read напрямую |
| сайт-образец | [[sumanrox--mimic]]; картинка-образец — `taste--image-to-code-skill` |
| сообщения в боте | `getUpdates` без подтверждения, файлы через `getFile` |

**Выход:** `материалы-владельца/ВЫЖИМКА.md` (что в каждом, что берём) и
**общий файл уроков** в `ОБЩЕЕ-ОСНАЩЕНИЕ` (пример: `УРОКИ-ИЗ-РОЛИКОВ.md`) со
ссылками из `СТЕКИ.md` там, где уроки нужны. Уроки общие, а не про одно дело.

## Ф5 — спецификация: шесть документов

**Инструмент — [[superplan-six-documents]]** (создан 19.09.2026 по опыту магазина):
продукт, техника, путь по экранам, дизайн, данные, этапы. Шаблоны и скрипт
контраста в папке скилла.

| Документ | Ворота |
|---|---|
| 1 продукт | «Готово, когда» — пункты да/нет, каждый проверяется запуском |
| 2 техника | факты о коде с `файл:строка`; внешние — первоисточник или «проверить» |
| 3 путь | у каждого экрана загрузка, пусто, ошибка, без сети |
| 4 дизайн | контраст посчитан скриптом по всем парам |
| 5 данные | настоящий SQL/типы; личные данные и закон |
| 6 этапы | что делает владелец; причина порядка; риски |

Запасные: [[gs-spec]] (выдача в задачу GitHub: берём фазы 3–4 и 14 стандартов
качества), [[ao-spec-driven-development]].

Попутно: **`ИДЕИ-ДЛЯ-<смежная система>.md`** — что улучшить в том, с чем
новое соединяется (просьба владельца 19.09.2026). Показывается владельцу в
конце фазы.

**Выход:** папка `спецификация/` из шести файлов; «да» владельца.

## Ф6 — план: задачи на один укус

**Инструмент — [[sp-writing-plans]].** Уточнения из практики:

1. **До плана проверить внешние факты**, на которых он стоит (методы API,
   лимиты, лицензии, наличие кириллицы в шрифтах) у первоисточника.
2. **Прочитать существующий код**, с которым стыкуется план, и собрать
   таблицу «что уже есть и берётся готовым».
3. **Полный код в плане — для опасных мест** (подпись, деньги и цены, повтор
   запроса, разбор входных данных, очистка HTML, потолки рассылок). Для
   экранов — контракт, состояния и проба. Отступление записать в шапку плана.
4. Каждая задача: файлы, проба сначала (FAIL), код, проба (PASS), коммит.
   Проба, которая ни разу не падала, не считается.
5. Контрольная точка владельца после каждого этапа.

Запасные: [[ao-planning-and-task-breakdown]], [[claude-mem-make-plan]].

**Выход:** `план/<дата>-<дело>.md`.

## Ф7 — ревью плана до работы

Самая недооценённая фаза: переделать план дешевле, чем код. 19.09.2026 ревью
нашло 8 проблем плана магазина, в том числе дыру в моей же очистке HTML.

| Скилл | Что делает |
|---|---|
| [[gs-plan-eng-review]] | шаг 0 (объём, что уже есть, встроенное вместо своего), затем архитектура → качество кода → тесты → скорость; каждая находка владельцу с вариантами и рекомендацией; обязательные разделы: «не входит», «что уже есть», схема отказов (тихий отказ без пробы = критический пробел), параллельные линии, отчёт с VERDICT в конце плана |
| [[gs-autoplan]] | четыре роли подряд: CEO, дизайн, инженер, DX |

Уточнения: служебные команды gstack на машине не стоят — журнал ревью в
манифесте; вопросы можно пачкой до 4, но **одна находка — один вопрос**;
своя найденная ошибка — сразу в `записать-ошибку.py`.

**Выход:** план с внесёнными решениями и разделом «Отчёт ревью плана».

## Ф8 — цель: закрепить «готово» до стройки

Владелец ставит цель командой `/goal` с критерием из «Готово, когда»
(1-ПРОДУКТ §1.6). Цель держит исполнение в рамке: работа не считается
законченной, пока критерий не выполнен и не доказан.

**Выход:** поставленная цель; ссылка на неё в манифесте.

| Шаг | Чем |

## Сквозное: всё время, в каждой фазе

| Что | Как |
|---|---|
| каждая ошибка, включая свою | сразу `записать-ошибку.py` (Python 3.11 по полному пути) |
| инструмент раньше рук | скилл → агенты (если разрешены) → MCP → три памяти; найденный скилл читать целиком и объявлять |
| цифры считать, а не прикидывать | контраст, вес, число сообщений, бюджеты — скриптом |
| пути Windows в коде | только Edit или сырые строки; после правки искать управляющие символы |
| заглушка ≠ работа | связность доказывает заглушка, работу — живой запуск и устройство |
| идеи смежным системам | `ИДЕИ-ДЛЯ-<система>.md`, показать владельцу |
| «один раз» | факт или предупреждение звучит один раз; повтор только перед необратимым действием |
| запрет классификатора | не обходить; сказать владельцу, что и почему заблокировано |

## Манифест — обязательная часть каждого суперплана

⚠️ **Суперплан без манифеста не считается начатым.**

| Раздел | Что держит |
|---|---|
| Цель | словами владельца |
| Готово, когда | проверяемый критерий (из 1-ПРОДУКТ §1.6) |
| Фазы | таблица Ф0–Ф10 с состоянием и ссылкой на файл-выход |
| Решения | М… (владелец) и Т… (техника): решение, причина, следствие |
| Факты | найденное в коде и замерами, со ссылкой `файл:строка` |
| Запреты | чего нельзя и почему |
| Журнал | что менялось, с датой |

**Правила ведения:**
1. Решение принято — записано в тот же момент.
2. Ответ владельца — по сути дословно.
3. Факт из кода — со ссылкой на файл и строку.
4. В шапке `состояние: идёт` или `состояние: закрыт`.
5. Новая сессия начинается с чтения манифеста.

## Как выбирать глубину

| Задача | Цепочка |
|---|---|
| правка в одну строку, известная причина | без плана; есть ли скилл под это |
| баг с непонятной причиной | Ф11 → Ф6 → Ф9 → Ф10 |
| новая возможность в существующей системе | Ф0 → Ф2 → Ф5 (коротко: продукт, техника, данные) → Ф6 → Ф7 → Ф9 → Ф10 |
| новый продукт, приложение, сайт | **вся цепочка Ф0–Ф10** |
| открытое решение, много путей | Ф0 → Ф1 → Ф2 → Ф4, дальше по обстоятельствам |
| чужой код, непонятная область | сначала `graphify query`, потом по обстоятельствам |

**Правило глубины:** чем дороже ошибка и труднее откат, тем раньше по цепочке
начинать. Там, где ошибка стоит денег и молчит (торговая система, магазин с
заказами), — начинать с начала.
